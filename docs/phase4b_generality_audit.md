## 数据与能力边界

Campaign Request 负责商品输入、事实、可选参考、用途、语言、尺寸、预算和审核策略。Agent 提交绑定图片/实例/版本的可见事实、真实细节窗口和创意文案；代码验证数据与证据，再自动计算布局与种子。缺少可靠视觉分析时输出待补充交接文件，不从文件名或分类猜测真实结构。

Shot Type 注册表定义适用条件、事实要求、策略、版式、真实性、平台和失败回退；输出数量及意图按请求/证据选择。参数未知则跳过规格，对比数据未验证则拒绝对比。Level 2 使用明确的环境广告面板，商品不假装与远景地面接触。Level 3 仅暴露能力/真实性接口并明确未实现互动，不伪造穿戴。

## 本轮文件范围与顺序

1. 新增 creative/campaign.py（请求/交接/事实）、intents.py（意图与场景门禁）、layouts.py（布局），及 campaign runner 和统一 CLI。
2. 最小修改 planning 的固定数量门禁和 marketing_renderer 的换行、动态总览及显式背景适配。
3. JSON 请求/Agent 分析数据分别绑定包袋、耳机、蓝盘；先包袋实跑，再耳机、蓝盘。旧资产、4A 配置、图片、工作流与执行日志只读保留。
4. 冷启动腕表：核心冻结后仅增加输入请求和分析，至少完成一张真实资产最小输出，并核对代码哈希不变。
5. 编写 skills/universal-product-creative/SKILL.md 和真实 CLI 交接说明；运行技能验证、原有 195 项和新增行为测试，输出三套真实图与验收报告。

验收不仅看测试数量：同一 CLI 的三个独立计划与至少 18 张真实输出、至少两种视觉方向、实际环境背景、事实不串 SKU、未审核前景不进入 strict、新商品不改核心代码。所有新资产仍待用户视觉审核。
